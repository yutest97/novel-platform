# 06 待定问题（Open Questions）

- 版本：v1.0（方案稿，待技术负责人审查）
- 状态：**未获批准。**

本文列出**我不能自行拍板**的问题。每个问题给出：背景、影响范围、建议选项与倾向。最终决定权在项目负责人 / 技术负责人。

---

## Q1 模型供应商与具体模型选型

- **背景**：适配层是 OpenAI 兼容协议，但具体接哪家、用哪个模型（决定生成质量、字数控制、成本、中文能力）未定。
- **影响**：直接决定 2500—4000 字/章目标能否稳定达成、成本模型、以及"单章分多次调用"的工程方案（一次长输出通常不稳）。
- **建议选项**：
  - A. 先用一个成本可控的强中文模型（如国内头部 API 或国际模型的中文能力），明确"生成质量以可用初稿为界"。
  - B. 支持多模型可配 + 作者可切换，但第一版只验证一个默认模型。
  - **倾向**：B 的架构 + A 的默认值（适配层多 base_url 已设计好，成本可控）。
- **待定**：具体供应商名单、Key 由谁提供、预算上限。

## Q2 单章生成是否允许"多次调用拼接"

- **背景**：一次 API 调用稳定输出 2500—4000 字较难，通常需按场景节拍分段生成再拼接。
- **影响**：影响一致性（分段拼接可能跨段断裂）、Token 成本、任务结构（一个 task 内含多个子调用）。
- **建议选项**：A. 按节拍分段生成 + 拼接（推荐）；B. 一次生成（风险高，易截断）。
- **倾向**：A，并让一致性检查兜底拼接断裂。

## Q3 一致性检查的实现形态

- **背景**：7 类检查（境界/战力/资源/物品/认知/时间线/伏笔）是"规则引擎 + 结构化数据比对"还是"LLM 复核"还是两者结合。
- **影响**：决定检出率、误报率、实现成本、是否需要额外模型调用。
- **建议选项**：
  - A. 结构化规则为主（境界/资源/物品/时间线/伏笔可用确定性规则 + 事件流水比对），LLM 为辅（战力/认知这类语义判断）。
  - B. 纯 LLM 复核（实现快，但不可靠、成本高、无法给确定性证据）。
  - **倾向**：A（能给出"原文证据 + 建议位置"的更可能是确定性规则 + 定位）。
- **待定**：每类检查的规则清单与阈值（如"战力倒挂"的判定标准）。

## Q4 PostgreSQL RLS 是否作为第二道防线

- **背景**：`03` §5 建议 RLS 兜底，但会引入实现复杂度（Prisma 对 RLS 支持、迁移、测试）。
- **影响**：安全纵深 vs 开发成本。
- **建议选项**：A. 启用 RLS；B. 仅应用层强制过滤 + 集成测试覆盖越权用例（`04` AT-SEC-*）。
- **倾向**：首版用 B（应用层 + 越权测试），RLS 作为二阶段增强；但需技术负责人确认安全要求等级。

## Q5 ORM 选型（Prisma vs Drizzle）

- **背景**：两库均 Apache-2.0，闭源可用。
- **影响**：迁移体验、类型安全、与 RLS/事务/`FOR UPDATE SKIP LOCKED` 的配合。
- **建议选项**：A. Prisma（生态成熟、迁移工具完善）；B. Drizzle（更贴近 SQL、轻量、类型推导强）。
- **倾向**：A，除非 Q4 启用 RLS 需要更贴近 SQL 的控制（RLS 用原生迁移也能做，不构成决定性因素）。

## Q6 导出 Word（.docx）的实现方式

- **背景**：`01` F-EXP-01 要求导出 Word；`00` 导出格式含 .docx。生成 .docx 需要写 OOXML。
- **影响**：若引入现成 docx 库，需核查许可证（部分文档库为 GPL/AGPL，有传染风险，见 `05` §6.2）。
- **建议选项**：
  - A. 自研极简 OOXML 生成器（只输出正文段落，够用且零传染风险）。
  - B. 引入宽松许可证的 docx 库（需先确认许可证，如 `docx`（MIT））。
  - **倾向**：优先 B 里 MIT 的 `docx`，若许可证有疑义则退回 A。
- **待定**：Word 导出的排版要求（是否需目录/样式/分章分页）。

## Q7 初始管理员账号的创建方式

- **背景**：系统无公开注册，第一个管理员怎么来。
- **影响**：部署流程与安全。
- **建议选项**：A. 首次部署种子脚本创建（密码由部署者注入，不落库明文）；B. 一次性初始化命令行。
- **倾向**：A，密码经环境变量注入 + 首登强改。

## Q8 账号上限 10 的统计口径

- **背景**：`00` §3.3 规定上限 10，需明确"10"是活跃账号还是含停用。
- **影响**：边界行为。
- **建议选项**：A. 含停用（总数 ≤10，停用不释放名额）；B. 仅活跃（停用释放名额）。
- **倾向**：A（更简单、更保守），写入 `00` §6.1 已按"active + invited"表述，需负责人确认。

## Q9 版本保留的存储增长与清理策略

- **背景**：正文版本只增不减，30 章 × 多版本 × 多稿会累积；10 人规模量不大，但需明确是否设清理。
- **影响**：磁盘、备份大小。
- **建议选项**：A. 首版不清理（历史完整优先）；B. 管理员可手动归档旧版本。
- **倾向**：A，二阶段再评估归档。

## Q10 模型调用的失败重试与降级策略

- **背景**：`04` AT-F1 要求失败不覆盖；需明确自动重试次数、退避、降级（换模型/换供应商）。
- **影响**：任务成功率与成本。
- **建议选项**：A. 自动重试 1 次 + 指数退避，不自动换模型；B. 支持配置降级供应商。
- **倾向**：A（首版简单可靠），B 作为可选配置项。

## Q11 生成内容的版权 / 内容合规责任

- **背景**：AI 生成中文小说，涉及内容合规（涉黄涉政等）与版权责任归属。
- **影响**：产品合规风险，非纯技术问题。
- **建议**：由项目负责人明确内容审核策略与责任边界；技术侧仅保证日志脱敏、数据私有。
- **待定**：是否需要内容安全过滤（可能引入第三方 API 或模型，成本与许可证另议）。

## Q12 一致性检查的"阈值与规则细节"

- **背景**：Q3 定了形态后，仍需逐类细化规则（例如：境界提升的最小间隔章数、战力跨阶判定的容差）。
- **影响**：误报率直接决定产品可用性。
- **建议**：由项目负责人 / 技术负责人（或懂玄幻的专家）提供规则初稿，实现方落地并标注可调参数。

---

## 汇总：需要负责人拍板的优先级排序

1. **Q1 模型供应商/预算**（最高优先，影响成本与质量基线）。
2. **Q2 单章多次拼接**（影响工程结构）。
3. **Q3 + Q12 一致性检查形态与规则细节**（影响核心卖点可行性）。
4. **Q6 导出 Word 的许可证**（涉及合规红线）。
5. Q4 RLS、Q5 ORM、Q8 上限口径、Q10 重试策略（工程取舍，可在阶段二前确认）。
6. Q7/Q9/Q11（流程与运营项，可稍后）。
